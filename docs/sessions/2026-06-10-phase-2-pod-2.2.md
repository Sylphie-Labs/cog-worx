# Session 2026-06-10 — Phase 2 Pod 2.2 (Latent Space on pgvector) — design lock

**Status:** Design **LOCKED**, implementation in progress (2026-06-10). Design ratified via mythos
deep-reasoning pass + Jim sign-offs on both flags. Session mirrors the pod-2.1 log format.
Supersedes the looser ROADMAP wording (now updated, `ROADMAP.md:173`).

## Scope (per ROADMAP)

Pod 2.2 — hot/cold latent space tiering on pgvector. Hot/cold tier membership as a
capacity-bounded top-N by ACT-R activation, recomputed by an atomic SQL sweep sweeper.

## Two facts from the port sources that reshaped the plan

1. **Sylphie has no tiering to port** — only frequency-weighted hydration (`use_count DESC,
   last_used_at DESC LIMIT 6000`, dies with process). In-memory tier is wrong for a framework
   (multi-process, no resident service). What ports: the capacity-bounded-working-set idea, the
   `recordUse` pattern, and the runner-up margin (deferred to Pod 2.6).
2. **Sylphie's hot-first-with-fallback is only sane behind its confidence gate** (similarity
   threshold 0.80 + runner-up margin). Without that gate, hot-first would rank 0.30-similarity
   hot rows above 0.90-similarity cold rows — a quality bug. Gate deferred to Pod 2.6; without
   it the default search semantics must be tier-agnostic.

## Locked decisions

- **D1 — Single table + `tier` column (capacity-bounded top-N):** two-table design rejected
  (double ANN index, union on every search, no uniqueness constraint across tables). Stored
  `activation_score` column rejected (stored derived state goes stale, no self-normalizing
  capacity, violates the 2.0/2.1 derive-at-read doctrine). Single table wins: tier flips are
  ordinary row UPDATEs, no union required, S8 lesion is clean (sweeper off → everything cold →
  default search byte-identical to a no-tier table), capacity bound is self-normalizing.
  *(Jim sign-off on Flag 1 — 2026-06-10.)*

- **D2 — ACT-R activation formula:**
  `activation = ln(1 + use_count) − d·ln(max(Δt_hours, ε))`
  with d=0.5 (ACT-R canonical, spike-checked) and ε=1/60 (one-minute floor preventing log(0)).
  Hot tier = top-`hot_capacity` rows by (activation DESC, use_count DESC, last_used_at DESC, id ASC).
  d=0.5 is NOT trusted as a ported constant — the spike includes a d ∈ {0.25, 0.5, 1.0}
  sensitivity check (lesson from the 2.1 lcb_quantile discovery: ported numeric constants must
  earn their place). No stored activation column (derive-at-sweep, not derive-at-store).

- **D3 — Seam changes (Jim approved 2026-06-10):** `upsert → put` (content-only; ON CONFLICT
  never touches use_count/last_used_at/tier/created_at), `record_use(ids) → int` (atomic
  in-place use_count += 1 for the given id set), `search(tier=None)` scope filter added.
  `sweep_tiers(now, hot_capacity)` added to the Protocol. `LatentRecord` drops `use_count`
  (a write-ignored field is a contract lie); `LatentMatch` gains tier/use_count/last_used_at
  for observability. Seam split is correct because `put` is idempotent but `record_use` is not
  — they cannot share a method without breaking the idempotency guarantee.

- **D4 — Sweeper:** `LatentTierSweeper` in `runtime/` (mirrors the Sweeper/Projector pattern
  from Pods 1.1 and 2.1). `tick()` delegates to `store.sweep_tiers(now=clock(), hot_capacity)`.
  No cursor, no lease, no visibility fence — the tier sweep is a pure function of the current
  snapshot, not a log consumer. S6 trivially satisfied: one UPDATE statement = one implicit txn;
  crash = rollback = table untouched, tier state recovers on the next tick.

- **D5 — Search semantics (Jim approved 2026-06-10):** Global exact top-k by cosine
  (tier-agnostic default). `tier=` filter scopes to hot-only or cold-only. Score is always pure
  geometry (1 − cosine distance), never tier-adjusted. Hot-first composite (two-call pattern:
  `search(tier="hot")` then `search(tier="cold")` to fill remainder) deferred to Pod 2.6 behind
  the confidence gate.

- **D6 — Schema migration:** Idempotent `ALTER TABLE … ADD COLUMN IF NOT EXISTS` ×3 (tier,
  created_at, last_used_at) in `ensure_schema`, placed AFTER the CREATE TABLE. Lesson from 2.1
  FIX-2: index/ALTER must come after CREATE, never before (a fresh-install table already has the
  columns from CREATE; a pre-2.2 upgrade cluster does not — the ALTER path must work on both).
  Backfills existing rows to tier='cold' and migration-time timestamps. Live migration test
  required (CF-6): migration paths with zero coverage hide upgrade crashes, as the 2.1 FIX-2
  proved.

- **D7 — Spike:** Two-part. (a) Structural invariants I1–I6, each with a bug-injection negative
  control (consistent with the standing red-team rule: mutation-resistant assertions before
  "validated"). (b) Judgment claim: composite ACT-R activation CI-better than frequency_only in
  W2 (regime shift) and W3 (burst-and-die) AND recency_only in W1 (stationary Zipf) AND never
  CI-worse than the lexicographic baseline. Scenarios: W1 (stationary Zipf), W2 (regime shift),
  W3 (burst-and-die), W4 (cold-start trickle). Pre-committed fallback: if composite never
  CI-beats lexicographic → ship lexicographic, defer ACT-R (a legitimate S12 outcome, identical
  to the TS deferral in 2.1). The d-sensitivity check (d ∈ {0.25, 0.5, 1.0}) runs inside the
  spike before the judgment claim is evaluated.

## Carry-forwards

- **CF-1 — Runner-up margin / confidence gate** (deferred to Pod 2.6): hot-first-with-fallback
  requires a similarity threshold (≥0.80) + runner-up margin check before preferring a hot result
  over a cold one. Without it, tier membership corrupts recall quality. Deferred deliberately
  because the correct threshold depends on the recall stack (Pod 2.5) being in place.
- **CF-2 — Thompson-style hot-tier promotion sampling** (deferred): weighted-random promotion
  of near-threshold cold rows (activation close to the boundary) to explore the tier edge. Out of
  scope until the activation formula is spike-validated.
- **CF-3 — ANN index strategy** (deferred): `pgvector` HNSW vs IVFFlat tuning for hot/cold
  split queries. For now a single flat index; splitting indexes per tier (or a partial index on
  tier='hot') is a performance pod.
- **CF-4 — `use_count` as event log** (upgrade path): if `record_use` ever becomes
  correctness-bearing (not just tier-placement), it must become an append-only event log with a
  projector (mirroring the 2.1 Trial pattern). Documented so a future pod doesn't increment
  in-place on a correctness-bearing counter.
- **CF-5 — d-constant empirical tuning** (deferred): d=0.5 is the ACT-R canonical value. The
  spike includes a sensitivity check (d ∈ {0.25, 0.5, 1.0}) but does not tune from user data.
  A future ops pod with real usage telemetry may tune d per-agent.
- **CF-6 — Live migration test** (in-scope for this pod, not deferred): must cover upgrade from
  a pre-2.2 latent table (no tier/created_at/last_used_at columns) to confirm `ensure_schema`
  does not crash on a real upgrade, consistent with the 2.1 FIX-2 lesson.

## Key tension documented

`record_use` is an increment-in-place counter — seemingly contradicting the 2.0/2.1
"derive at read, never mutate" doctrine. Resolution: the doctrine applies to logical-step facts
that bear on correctness (trial outcomes, posteriors, promotion gates). `use_count` is a
physical-event tally that bears only on tier placement. A replay never re-executes search (S6 —
stored outputs), so the count cannot drift on the path S6 protects. The failure mode of a
slightly-wrong count is a slightly-wrong tier, and search correctness never depends on tier (D5:
score is always pure geometry). If `use_count` ever becomes correctness-bearing it must become
an event log (CF-4). This tension is intentional and resolved by the S6 stored-outputs guarantee;
it is documented here so a future reader does not reflexively "fix" it by moving to a derive-at-read
pattern that re-executes searches on replay.
