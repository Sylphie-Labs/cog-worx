## What landed

- **`AwaitHuman.to`** (`loop/result.py`). A committed `AwaitHuman` now REPLAYS as a plain advance to
  `to`, mirroring the `Wait` precedent exactly — the missing piece that made await-human a dead-end.
- **Human-input journal seam** (`substrate/journal.py` + `adapters/timescale_journal.py` +
  `testing/doubles.py`): `record_human_input(run_id, step_index, answer)` —
  **first-answer-wins** (`INSERT … ON CONFLICT (run_id, step_index) DO NOTHING`, new
  `cogworx_human_inputs` table) — and `read_human_input(...) -> Artifact | None`. The answer rides the
  **TimescaleDB** journal (S3/S6), keyed to the await-human step's `seq`.
- **Pull-based injection** (`runtime/context.py` + `loop/stage.py`): `ctx.read_human_input(step_index)`.
  A downstream stage PULLS the answer and routes **structurally** on its `data` (S9) — never the engine
  pushing a mutable `ctx.human_input` (which would be replay-fragile). Deterministic on every replay
  because the answer is read from the journal by key.
- **`Engine.provide_human_input(run_id, *, payload, kind, confidence)`**: rehydrate → guard
  `AWAITING_HUMAN` (else no-op return) → resolve the await-step `seq` (the last committed step) → build
  the answer `Artifact` with `Provenance(source="human", recorded_at=clock())` (S5 honesty by
  construction, mirroring `_exhaustion_degraded`) → **`record_human_input` BEFORE the CAS** (the hard
  ordering constraint) → emit `HUMAN_INPUT_RECEIVED` → CAS `AWAITING_HUMAN→RUNNING` (loss → return
  state; first-answer-wins under concurrent answer) → emit `RUN_RESUMED` → re-drive. The committed
  `AwaitHuman` then replays as advance-to-`to`; it is never re-run (S6).
- **`HUMAN_INPUT_RECEIVED`** event (`coordination/events.py`, Subsystem.SPINE).

## Validation (the discipline caught a real run-stranding gap)

- **Architect (pre-code)** confirmed the design and corrected three subtle points: (1) declare
  `AwaitHuman.to` in the stage's `transitions` so `_edges()`/`pathway_fingerprint` already cover it (no
  fingerprint change — sidesteps the 1.2 `exhausted_to` trap); (2) **pull, not push** for the answer
  (replay determinism); (3) **record-before-CAS** is a hard correctness constraint.
- **Spike (tests-first, mutation-resistant):** H1/H1b approve+reject structural branch · H2 concurrent
  first-answer-wins (drives once) · H3 record-before-CAS crash · H4 cold resume of an answered run, zero
  model calls · H5 unanswered resume no-op · H6 non-AWAITING no-op · S1/S5/S6/S9 invariants.
- **Red-team (two passes).** Pass 1 found **FINDING B (MED, reproduced):** a stage routing to an
  **undeclared** `to` (existing-but-undeclared → silent wrong-route; nonexistent → `StageGraphError`
  inside `_drive` *after* the human answered + the answer was durably journaled → run **stranded
  RUNNING**). **FINDING A (rated HIGH, adjudicated down):** the architect confirmed `result.to` cannot
  live in a static fingerprint (it's a runtime value; the docstring already scopes behavioural changes
  to the version-bump convention) AND a committed `AwaitHuman` replays its **journaled** `to`, so a
  parked run's route is immutable across an in-place edit — the claimed "resume reroutes" exploit does
  not hold. A collapses into B.
- **Fix (architect-prescribed):** a runtime **declared-route guard** in `_drive`'s fresh branch,
  **before** `commit_step`: a fresh result's non-None `to` must be in **`graph.edges_from(current)`**
  (NOT `transitions_from` — the engine's own exhaustion `Degraded(to=exhausted_to)` must pass; that was
  the one likely impl bug, covered by an explicit positive regression test). Uniform across
  Transition/Wait/AwaitHuman/Degraded; skips `Done` and `Degraded(to=None)`; excluded on replay (S6
  trusts the journal). A bad `to` now fails loud at first execution with nothing committed.
- **Red-team pass 2** re-attacked the guard: held under every mutation (proved non-vacuous via the
  `transitions_from` mutation and the commit-then-guard mutation), both honesty docstrings accurate.
- **Honesty corrections (red-team-driven):** the engine's blanket "exactly-once EXECUTION" docstring was
  **scoped** to the CAS-guarded entrypoints (`fire_timer`/`unpause`/`provide_human_input`), naming
  `resume(RUNNING)` double-execute-of-side-effects as the **deferred run-lease/reaper** gap; the
  `pathway_fingerprint` docstring now names result `to` as out of the structural fingerprint's domain.
- **CANON: COMPLIANT** (S1–S12, §3/§4). No violations.

## Carry-forward (NOT a 1.3 gap)

- **`resume(RUNNING)` double-execute of an uncommitted side effect** — the bare crash-resume path takes
  no CAS, so two concurrent resumes of the same RUNNING run can fire a stage's side effect twice (the
  journal commit stays exactly-once on `(run_id, step_index)`). This is the **deferred run-lease +
  heartbeat + stranded-RUNNING reaper** ops pod (CANON §3/S7); honestly documented, not fixed here.
- **Poisoned/legacy committed `to` on replay** (LOW) — a committed `to` no longer in `edges_from`
  (legacy pre-guard row or a foreign engine writing the same journal) detonates with a raw
  `StageGraphError` from `graph.get` rather than a friendly `ResumeError`. Fail-loud, not silent;
  unreachable for runs written by this engine (the fresh-path guard prevents committing such a row). A
  future hardening could wrap the replayed advance in a `ResumeError` for operator clarity.
