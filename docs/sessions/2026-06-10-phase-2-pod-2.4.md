# Session 2026-06-10 — Phase 2 Pod 2.4 (World model + user model) — implementation

**Status:** VALIDATED 2026-06-10. All flags approved by Jim (F1–F4). Red-team gate PASS (3 findings fixed post-implementation — see Red-team gate section). 572 unit + spike tests passing, 1 xfail (pre-existing Pod 2.1 known limitation).

## Scope (per ROADMAP)

Pod 2.4 — world model + user model. Long-term/user knowledge as governed views over the 2.0 claim layer (scoping, write-token discipline per S7).

## Design port and reshaping facts

1. **Scope sits on `(:Claim)` not `(:Entity)`** — entities are shared topology anchors across scopes; contested state lives in claims. This enables the Pod 2.5 recall stack to traverse entity links across scopes without scope-partitioned topology.

2. **Scope joins claim identity** — `claim_id_for(s, p, o, scope="world")` produces a different ID than `claim_id_for(s, p, o)` (which uses the default `"agent"` scope). When `scope == "agent"` the hash is byte-identical to the pre-2.4 3-part encoding. Existing claim IDs are stable.

3. **`ScopeRegistry` + `ScopeWriteToken`** — mirrors the Pod 2.3 `SourceRegistry` pattern. First call to `claim_write_token(kind, ref, owner=X)` binds X; same-owner re-call is idempotent; different-owner re-call raises `ValueError` (S7 fail-loud).

4. **`ScopedKG`** — concrete `@final` class wrapping `EntityKG`. Not a Protocol (no new seam needed — the view does no I/O of its own). `assert_fact` mints both `Claim` and `EvidenceEvent` internally; callers never construct scoped Claims directly.

5. **`ClaimExtractor` unchanged** — stays `"agent"` scope. Routing model-extracted content into user/world scope would make model-emitted subject text a scope-routing signal (S9 violation). Automated promotion defers to Pod 2.7.

## Locked decisions

- **D1 — Scope as property on `(:Claim)`:** `claim.scope: str = "agent"` (additive field, migration-free). Read path uses `coalesce(c.scope, 'agent')` for pre-2.4 nodes.

- **D2 — Scope joins claim identity (conditional hash):** 3-part hash for `scope="agent"`, 4-part for non-default. Existing claim IDs are stable.

- **D3 — `ScopeRegistry` enforces S7 in-process.** Cross-process exclusivity deferred to the orchestration platform (contracts-now, platform-later; consistent with the run-lease/reaper deferred ops pod).

- **D4 — v1 feeders are explicit governed writes only.** `ClaimExtractor` unchanged.

- **D5 — Permanent scope ID literals:** `"agent"` (default), `"world"`, `"user:{nfc(user_id)}"`.

- **D6 — `ScopedKG` is NOT exported from `cogworx.knowledge.__init__`** (it imports from the substrate layer, which would break the S1 isolation invariant). Callers import from `cogworx.knowledge.scoped_kg` directly.

## Carry-forwards

- **CF-1 — `ScopeWriteToken` forgery prevention:** `ScopeWriteToken` is a frozen dataclass; runtime type-enforcement against string injection relies on structural discipline, not Pydantic validation. If S7 needs airtight runtime forgery prevention, `ScopeWriteToken` should become a Pydantic model with a `Scope` validator (flagged by test-qa-expert in SC-7 analysis).

- **CF-2 — Factory-with-clock variant:** `world_model`/`user_model` factory functions do not thread `_clock` — injectable clock requires constructing `ScopedKG` directly. A factory-with-clock variant is deferred.

- **CF-3 — Vector over-fetch re-query floor:** `k' = max(4k, 64)` post-filters in Python and does not re-query if underfilled. Full recall guarantee for scoped similarity queries deferred (accepted v1 floor, documented in adapter).

- **CF-4 — Automated agent→user/world promotion:** `ClaimExtractor` stays `"agent"` scope. Explicit promotion-with-provenance surface defers to Pod 2.7.

- **CF-5 — Cross-process scope exclusivity:** S7 letter ("exactly one write-token per entity") is enforced in-process by `ScopeRegistry`; across processes it is deferred to the orchestration platform (same pattern as the run-lease/reaper ops pod carry-forward).

## Key tensions documented

1. **Why scope on `(:Claim)` not `(:Entity)`?** Entities are shared topology anchors — scoping the entity would partition the graph and prevent Pod 2.5 recall from traversing cross-scope entity links. Scoping the claim keeps the topology connected while isolating contested state per knowledge domain.

2. **Why `ScopedKG` is `@final` and not a Protocol?** The view does no I/O of its own — it is a thin governor over an existing `EntityKG` instance. Adding a Protocol would create a new seam where none is needed (CANON S3: seams for substrate engines, not for view wrappers). `@final` prevents accidental subclassing that would bypass the token discipline.

3. **Why is `ScopedKG` not exported from `cogworx.knowledge.__init__`?** `scoped_kg.py` imports from the substrate layer (`cogworx.substrate.entity_kg`). Exporting it from `cogworx.knowledge.__init__` would pull substrate imports onto the model-layer import path, breaking the S1 isolation invariant. The same pattern applies as D6: callers import from `cogworx.knowledge.scoped_kg` directly.

4. **Why is `ClaimExtractor` left at `"agent"` scope?** Routing model output into user or world scope requires the model's emitted subject text to serve as a scope-routing signal — a direct S9 violation. Structural promotion (code-authored policy, not model-emitted) is the correct design, deferred to Pod 2.7.

## Red-team gate — PASS (2026-06-10)

Verdict: CONDITIONAL → all minimum fixes applied → VALIDATED. 572 tests passing.

**Issues found and fixed:**

- **CRITICAL C-1 — K4 vacuous accumulation assertion:** `assert len(evidence) >= 1` passed even when the second `write_claim` call was a no-op (evidence not appended). Fixed: changed to `assert len(evidence) == 2` + added a mutation-resistant negative control (`test_k4_negative_control_no_accumulate_bug`) that monkeypatches `InMemoryEntityKG.write_claim` to skip the second evidence append and confirms the positive assertion would fail.

- **HIGH H-1 — SC-4 multi-registry same-process S7 bypass:** Two `ScopeRegistry` instances in the same process can each independently claim the same scope, giving two writers silently — the spike verdict "token discipline: verified" was misleading. Fixed: added `test_sc4_multi_registry_same_process_known_gap` which documents and proves the gap (asserts `id_a == id_b` and `len(evidence) == 2` — two writers hit the same claim), corrected the SC-4 conclusion to say "verified within a single registry instance," documented as CF-6.

- **HIGH H-2 (carry-forward) — SC-7 conclusion overreach:** SC-7 stated "S9 structural forgery prevention: verified" without scoping to JSON-path only. Fixed: qualified the SC-7 docstring to name exactly what is verified (accidental model-text→token JSON coercion) and what is not (direct Python construction = explicit, reviewable breach, CF-1).

**Medium carry-forwards (not blocking):**

- **CF-6 — Multi-registry same-process S7 gap:** Two `ScopeRegistry` instances in the same process can each claim the same scope. Resolution discipline: use ONE `ScopeRegistry` per `EntityKG` in the application. Cross-instance enforcement defers to the orchestration platform (CANON §3/S7 contracts-now). Documented in `test_sc4_multi_registry_same_process_known_gap`.

- **CF-7 (née M-2) — Non-canonical scope strings:** A directly constructed `Claim(scope='AGENT')` creates a phantom claim node invisible to canonical reads. Unreachable through `ScopedKG.assert_fact` (always derives scope from `token.scope.scope_id`). No structural guard at the `Claim` boundary. Documented in the CF-6 block in the spike file and in `assert_fact`'s docstring.

- **CF-1 (H-2, existing) — Direct `ScopeWriteToken` construction:** `ScopeWriteToken(scope=Scope(...), owner="attacker")` bypasses the registry. Structural discipline only; SC-7 conclusion now explicitly scoped to the JSON path.

- **M-1 (existing CF-2) — Factory `_clock` threading:** `world_model`/`user_model` factories do not thread `_clock`; injectable clock tests bypass factories. Carry-forward documented.
