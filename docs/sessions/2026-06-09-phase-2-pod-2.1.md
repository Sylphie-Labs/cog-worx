#### (Historical) BLOCKER — internal contradiction in the locked read predicate (architect to resolve): FP-1
(completeness under overflow + control-burst — the P0-1 gate) FAILS against the spec as written. The
locked row filter is the **scalar-`committed_at` lookback floor** `committed_at > k.committed_at -
lookback`, ordered by the keyset, LIMIT `batch_limit`. When **N rows share ONE `committed_at` window and
N > batch_limit** (exactly the FP-1 construction), the floor `k.committed_at - lookback` is CONSTANT (the
cursor's `committed_at` never rises), so every tick's `ORDER BY … LIMIT batch_limit` re-cuts the SAME
lexicographically-smallest prefix — which in FP-1 are the control steps — and the cursor parks at the end
of the control prefix forever. The procedure rows behind them are never reached → **the scalar-floor
predicate re-livelocks P0-1**, the very bug it was meant to kill. The keyset cursor advance is wasted
because the read predicate consults only `k.committed_at`, not the full keyset. The spec explicitly warns
against a strict `> (committed_at, run_id, step_index)` keyset as the **ONLY** predicate (that re-breaks
P1 by excluding late rows) — but the scalar floor as the only predicate re-breaks P0-1. Resolving this
needs the architect: the read must guarantee progress **within a single `committed_at` window** (a strict
keyset `> k` lower bound for the limited scan) AND still catch late rows below the cursor (the lookback
band) — these two pull opposite directions under one ordered+limited scan, so it likely needs a
low-water/high-water cursor pair or a separately-bounded band re-scan. FP-1 is left FAILING (not xf,
not deleted) so the contradiction stays loud until the architect decides.

## Pod 2.1 STRUCTURAL FIX (2026-06-10) — `commit_xid` visibility-fenced ordering (mythos, Jim option a)

The two-read keyset+band apparatus above was a workaround for the **non-monotonic, multi-writer
wall-clock `committed_at`**: a single forward read could not be both complete (catch late rows) and
livelock-free, so it needed a lookback band, a transient band sub-cursor, a ceiling, and a
`max_clock_skew` assumption. mythos found (and verified live on PG16) the structural fix Jim approved:
order projection by a **DB-assigned commit-order integer** and read with a **visibility fence**. This
**DELETES the entire band/floor/lookback apparatus**. The write path (S6) stays **byte-identical**.

### The design (verified live on PG16)
- `cogworx_journal_steps` gains `commit_xid bigint NOT NULL DEFAULT (pg_current_xact_id()::text::bigint)`.
  It self-populates **inside the writing txn** — `commit_step` changes ZERO lines and still names only
  `(run_id, step_index, stage_name, result, committed_at)`.
- The projector reads with **TWO clauses**: the **FENCE**
  `commit_xid < pg_snapshot_xmin(pg_current_snapshot())::text::bigint` (forbids consuming any row an
  in-flight txn could still slot below — closes the sequence-visibility race) **AND** the strict keyset
  `(commit_xid, run_id, step_index) > cursor` (omitted on cold start). `ORDER BY (commit_xid, run_id,
  step_index)`, `LIMIT`. The **ORDER BY leading column and the fenced column are BOTH `commit_xid`** (a
  hybrid seq+xid is provably wrong). xid8 handled as BIGINT end-to-end via `::text::bigint`.
- `committed_at` stays exactly as-is (injectable clock; Phase-1 replay/timer determinism +
  `Trial.occurred_at` depend on it). It is no longer a cursor/ordering key.

### Seam changes
- **`substrate/journal.py`** now owns the projection types (fixes the old import inversion):
  `ProjectionCursor(commit_ordinal: int, run_id: str, step_index: int)` REPLACES `KeysetCursor`;
  `ProjectedStep(record: StepRecord, commit_ordinal: int)` (non-optional ordinal — reads always carry
  it, keeps `StepRecord` frozen). New seam: `committed_steps_after(cursor, *, limit) -> Sequence[
  ProjectedStep]` (NO lookback, NO ceiling). `procedural_kg.py` imports `ProjectionCursor` from
  `journal.py` (no cycle).
- **`procedural_kg.py`**: `KeysetCursor`/`keyset_ge`/`keyset_max`/`floor_keyset` → `ProjectionCursor`
  (in journal) + `ordinal_ge`/`ordinal_max`. `project_batch(consumer, *, trials, progress)` (band
  dropped). `read_band` deleted.
- **`neo4j_procedural_kg.py`**: `_WRITE_CURSORS_CYPHER` collapsed to advance-progress-only
  (`_ADVANCE_CURSOR_CYPHER`); band columns + `_READ_BAND_CYPHER` deleted. The cursor ordinal is a plain
  Neo4j **integer** — the ISO-string lexicographic storage hack is gone. `read_cursor ->
  ProjectionCursor | None`; old `(:ProjectionCursor)` nodes lack `commit_ordinal` -> returns `None` ->
  automatic cold re-projection (no-op end state under first-write-wins MERGE + run-grain dedup).
- **`runtime/projector.py`**: collapsed to a **single fenced read** tick (read cursor ->
  `committed_steps_after(cursor, limit)` -> resolve/stage via the UNCHANGED `resolve_outcome` path ->
  `project_batch(progress=cursor_of(last scanned row))` -> return count). `lookback_lag` deleted; the
  `clock` ctor param was dead post-redesign and is deleted.
- **In-memory double** (`testing/doubles.py`): `InMemoryJournal` assigns a strictly-increasing
  `commit_ordinal` per `commit_step` (the mirror of `commit_xid`; no MVCC so no fence needed — strict
  keyset over the ordinal is total). `InMemoryProceduralKG` drops the band, uses `ordinal_ge`.
- The **7 delegating test-double journals** drop the `lookback`/`ceiling`/old-`cursor` params and
  forward `committed_steps_after(cursor, limit=limit)`.

### A1-A4 assumptions / falsifiers (mythos)
- **A1 — `commit_xid` is monotonic in commit order on one cluster.** `pg_current_xact_id()` returns the
  xid8 of the assigning txn; the visibility fence on `pg_snapshot_xmin` guarantees a consumer only sees
  a row once no in-flight txn could commit below it. *Falsifier:* S1 + S6 (the fence holds back
  uncommittable-below rows; the unfenced control loses them). *Bound:* single Postgres cluster — xid8
  is not comparable across clusters/restores. Documented; cog-worx is single-cluster (S3).
- **A2 — `commit_step` never names `commit_xid`.** The DEFAULT self-populates inside the writing txn.
  *Falsifier:* a5 static grep + runtime probe (S3).
- **A3 — old `(:ProjectionCursor)` nodes migrate safely.** They lack `commit_ordinal` -> `read_cursor`
  returns `None` -> cold re-projection, a no-op end-state under first-write-wins MERGE + run-grain
  dedup. *Falsifier:* a4 byte-identical re-run (the re-projection converges).
- **A4 — single step per commit txn (Phase-1).** `commit_ordinal` ties are broken by `(run_id,
  step_index)`. **LATENT NOTE (`run_id COLLATE "C"`):** if a future pod batches MULTIPLE steps per
  txn, they share one `commit_xid` and the `run_id` tie-break must sort under a **byte-stable collation

  commits one step per txn, so this is dormant — flagged so a multi-step-per-txn batching pod adds the
  collation rather than discovering a silent locale-dependent ordering drift.

### FIX 1 — `run_id COLLATE "C"` pinned on the projection read (resolves the A4 OSS-collation note)
The A4 LATENT NOTE above is now ACTIVE, not just for a future multi-step-per-txn batcher: a published
OSS user on an ICU/locale-default Postgres gets DB ordering of `run_id` that diverges from the
Neo4j-side Python-codepoint cursor (`ordinal_ge`/`ordinal_max`, `procedural_kg.py`). Not data loss
(the red-team proved that — the MERGE on `trial_id` is first-write-wins, run-grain deduped), but a real
cross-collation re-projection-churn smell our C.UTF-8 test cluster cannot catch.
- `_read_projection` (`adapters/timescale_journal.py`): the strict keyset is rewritten from the
  row-value tuple `(commit_xid, run_id, step_index) > (...)` to the EXPANDED equivalent
  `commit_xid > x OR (commit_xid = x AND (run_id COLLATE "C" > r OR (run_id = r AND step_index > s)))`
  so the `run_id` tie-break can carry `COLLATE "C"`. Verified live: COLLATE is NOT honored per-element
  INSIDE a row-value tuple `(a, b COLLATE "C", c) > (...)` on PG16 (it returned all rows), so the
  expanded form is REQUIRED, not stylistic. Semantically identical to the tuple keyset;
  `commit_xid`/`step_index` are numeric (no collation). The `ORDER BY` pins the SAME
  `run_id COLLATE "C"`.
- The `cogworx_journal_steps_commit_xid` index is now built `(commit_xid, run_id COLLATE "C",
  step_index)`. This is load-bearing for the FIX, not cosmetic: EXPLAIN on a DEFAULT-collated index
  with `ORDER BY ... run_id COLLATE "C"` forces an **Incremental Sort** (index presorted on
  `commit_xid` only); the C-collated index makes the ORDER BY fully index-satisfied on ANY cluster
  collation. Verified live on the real cogworx table: `Index Scan using
  cogworx_journal_steps_commit_xid`, fence = `Index Cond`, keyset = `Filter`, **NO Sort node**.
- Comments added at the predicate, the ORDER BY, and the index explaining WHY (must match the
  Neo4j-side codepoint cursor; OSS portability).

### LATENT BUG SURFACED + FIXED by FIX 2 (in-scope: the migration path itself)
Writing the migration test surfaced a real pre-2.1 UPGRADE crash that had ZERO coverage: `_SCHEMA`
created `cogworx_journal_steps_commit_xid` on `commit_xid` BEFORE `ensure_schema` ran the ALTER that
adds the column (`_MIGRATE_COMMIT_XID` runs AFTER `_SCHEMA`). On a fresh install the column is in the
CREATE TABLE so it worked; on a real pre-2.1 cluster the `CREATE TABLE IF NOT EXISTS` is a no-op
against the old (no-`commit_xid`) table and the index DDL then errored `column "commit_xid" does not
exist` — `ensure_schema()` would have crashed on every real upgrade. Fix: the commit_xid index now
lives ONLY in `_MIGRATE_COMMIT_XID` (after the ALTER guarantees the column); `reset()` runs
`_MIGRATE_COMMIT_XID` too so the test-only recreate path keeps the index. This was pre-existing (the
index referenced `commit_xid` the same way before the COLLATE pin) and is exactly the gap FIX 2 names.
